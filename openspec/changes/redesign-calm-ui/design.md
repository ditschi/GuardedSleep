# Design

Roles applied: Product Owner, UX (designer and five reviewer perspectives: parent at 3 AM, grandparent, traveller with colour-vision deficiency, accessibility and interaction, visual design), Technical Architect, Critical Reviewer; Security/Privacy only for the font and copy checks in §10 and §14. Owner decisions of 2026-11-14 in §15. Review history at the end.

The decided mockup is [`mockup/mockup.html`](mockup/mockup.html) (54 frames, token panel, EN/DE copy table). It is generated by `mockup/gen.py` with `gen_css.py` (tokens) and `gen_table.py` (copy table); `mockup/render.sh` re-renders it to PNGs. `mockup/concept.md` and `mockup/changelog.md` are the designer's notes per round. Frame numbers below refer to the mockup. The mockup loads no web font: it names Plus Jakarta Sans and falls back to the system font unless the font is installed locally, so opening it sends no request to a third party; the apps bundle the font (§10). `mockup/gen.py` is the source of the mockup and is treated as a design document; the generated `mockup.html` is committed on purpose as the reviewed artifact (it is not build output of the product, and `gen.py` reproduces it byte for byte).

## Context

State on `origin/main` (2026-11-14, `fb0de8de`):

- **Android** (`apps/android/app/.../ui`): Material 3 with a dark theme by default (`theme/Theme.kt`: hand-picked colours, a yellow `Yellow`/`KioskYellow` for level 0), screens in `screens/` (role home, parent monitor, alert screens, baby kiosk, settings as one list). The parent ambient bar is green when connected. Listen is hold-and-slide-to-lock. Up to two saved connections per role (#56), talk-back (#55), a role-based start mode with "Use as default" (`alternate-roles-and-apk-size`) and an optional default parent connection that starts monitoring once per app start (#61, `parent-pairing-entry`). Alert style "Discreet", "Snooze" 10/30 min.
- **Web** (`apps/web/src`): Svelte 5 screens (`RoleScreen`, `ParentMonitorScreen`, `LinkAlarmScreen`, `NoiseAlertScreen`, `SettingsScreen`, `BabyMonitorScreen`), CSS in `lib/ui/theme.css`, "Night screen" overlay (`NightScreen.svelte`), no saved pairings, always the "Sound" style.
- **Core:** `LinkStatus` carries `state` (`connecting` before the first verification in this run, else `reconnecting`), `level`, `cause`, `acknowledged_until` and `last_alive_ms`; levels run from `last_alive` or, before the first verification, from the start of the run (`link.rs`, `down = now − last_alive.unwrap_or(started_at)`).
- **Specs:** `link-supervision` renders level 0 yellow, `connection-status` blue: a contradiction this change resolves.

## Goals / Non-Goals

**Goals:** one calm, modern visual system on both clients; a connected night looks quiet and every change is unmistakable; status words a tired parent understands without knowing the architecture; every state said once, in colour, symbol and words; settings that are easy to find; night mode that never hides a safety signal; implementation in PR-sized slices.

**Non-Goals:** new alert behaviour or timing, new core states, tablet-specific layouts, a diagnostics view, the alarm tones themselves, talk-back behaviour, role renames.

## Decisions

### 1. Visual direction

- **Option A — "Calm Night":** ink-navy surfaces, warm off-white text, one apricot accent for actions, a capsule status at the top, a status halo as the focal point.
  - Pros: the calmest at night; clear rule "accent = action, never status".
  - Cons: the halo is decorative and carries no data; the apricot accent sits next to the orange stage colour; little structure for many states.
- **Option B — "Precision Instrument":** graphite, hairlines, cyan accent, a status rail on every screen, a 4-step escalation ladder, tabular numerals, a 60 s level history with the real threshold.
  - Pros: the status rail and stage progress make "where am I, what comes next" obvious; honest data.
  - Cons: feels clinical; a strong fill at every level is loud at night; cyan collides with the blue stage colour.
- **Option C — "Warm Adaptive":** Material 3, plum-black "Dusk" and light "Day", a red-shifted "Ember" night scheme, crescent/horizon motif, Home with both roles, everything urgent in the thumb zone.
  - Pros: modern and warm; the Home structure solves mode choice; night scheme built in; safety colours already outside the theme.
  - Cons: alone it was too expressive (glow, gold accent near caution yellow, a ring gauge that collided with text).
- **Option D — combination:** C's structure and look, calmed with A's restraint (no glow, neutral connected state, accent only for actions), B's always-visible status bar, stage progress and tabular numerals.
  - Pros: keeps the strongest part of each; the reviews converged on it (round 3: 8–9 of 10).
  - Cons: one more design round than picking one; the token set is larger (three schemes plus fixed safety palettes).

Recommendation: D. **Decided: D (owner, 2026-11-14).** A, B and C alone move to Discarded alternatives.

### 2. Navigation and mode switching

- **Option A — one Home with both roles and their saved connections** (frame 01): role headers "Parent device" / "Baby device", each with up to two connection rows ("Start", the other device's name, last used), "Set up new devices" per role, a gear to Settings. Starting a row starts that role with that connection. While monitoring there is no switching: the way out is Stop monitoring (confirm, frame 23) → Home → choose.
  - Pros: one screen answers "what is this device doing tonight"; the connection is the mode, which matches how parents think ("Nursery", "Travel cot"); no hidden role switch; satisfies `alternate-roles-and-apk-size` "Switching mode" (no switch while monitoring).
  - Cons: replaces the role screen plus "Switch mode" flow that just shipped; needs a follow-up delta once that change is archived (§14).
- **Option B — keep the role screen and "Switch mode", restyle only.**
  - Pros: no spec change for device-setup.
  - Cons: two steps where one suffices; reviewers found "Switch mode" abstract (round 1, grandparent and traveller).
- **Option C — allow switching the connection from the monitor's More sheet** (round 0 mockup).
  - Pros: fast for travellers.
  - Cons: contradicts "no switch while monitoring"; a preselected radio could start the wrong connection; reviewed as a spec break (round 1, critical).

Recommendation: A. **Decided: A (owner, 2026-11-14).** The built automatic start (`parent-pairing-entry`) stays as built: a marked parent default starts monitoring once per app start, and "Choose another connection" stops it and shows Home (the mockup's "Wrong connection?" line on frames 09, 24, 25 uses that action). The mockup's frame 53 note "it never starts monitoring by itself" is **not** followed (§15, owner rule "follow the built behaviour").

### 3. Settings structure

- **Option A — two groups** (frames 18, 19, 21, 22, 53): **Connections** (saved connections per role; rename, forget; read-only while monitoring with "Stop monitoring to change connections") and **This device** (Alerts, Sound detection, Display, Open at start, Check setup, Language, About, Advanced). The status bar stays on top while monitoring.
  - Pros: separates "who I am paired with" from "how this phone behaves"; read-only rows prevent changing the pairing under a running session; Advanced keeps the risky settings (`device-setup` "Settings in Basic and Advanced" unchanged).
  - Cons: one more level for Language and About.
- **Option B — one long list with section headers** (today).
  - Pros: no navigation depth.
  - Cons: long; risky and harmless settings next to each other; the default connection had four names in four places (round 1, accessibility).

Recommendation: A. **Decided: A (owner, 2026-11-14).** "Open at start" (This device) holds the start mode (_Ask every time_ stays the default, owner Q2) and the parent's automatic-start connection, as built by `alternate-roles-and-apk-size` and `parent-pairing-entry`; moving the controls from the role screen and Home into this page needs the follow-up deltas of §14. The connection alarm tone row sits in This device › Alerts and is specified by `add-connection-alarm-tone`.

The full EN/DE copy, including every step, is in the mockup's copy table; ★ marks keys tagged `critical`.

**Core input needed (additive, read-only, no behaviour change):** the counter and the next-stage clock time need the start of the outage also before any contact (today `last_alive_ms` is `None` while connected and before the first contact; while `connecting` it is set only after a first contact) and the time of the next level, which depends on the configurable `alarm_after_ms`. Add `down_since_ms` (last contact, or the run start before any contact) and `next_level_at_ms` (`None` while connected, at level 3, while acknowledged, and in `peer_stopped`, `failed_needs_user` and `stopped`) to `LinkStatus` (`link-supervision` "Link states" and "Outage timing fields"). Both come from stored timestamps plus thresholds, never from `now`, so they stay constant within a level and the status is not re-emitted on every 500 ms tick (`LinkStatus` is emitted only when it changes). The platform converts them to clock time with its own reading of the same clock (web: the clamped `Date.now()`). Without them the UI would duplicate the thresholds, which AGENTS.md §5.1 forbids.

**Not taken from the mockup:** the pinned "Turn sound back on now" on the acknowledged screen (frame 26) needs a new core input that ends an acknowledgment early; the core has none. The acknowledged screen keeps "Try now" in the cause card and no filled action. The idea is added to `docs/backlog.md` (parent-alerts) by this change.

### 5. Night mode

- **Option A — Ember, manual, Off by default, Off · On · Automatic with a time window** (frames 05, 07, 21, 35, 49): Ember is a red-shifted scheme on black (text `#C98A7A`, variant `#A87365` at 5.0:1, outline `#9A5E50` at 3.6:1); dimness comes from the backlight, not from low contrast. One control in the monitor's More sheet, the monitor tool row and Settings › Display; a manual change wins until the next automatic change. Alerts, the status bar from the orange stage on, warning banners, grey and red bar states and safety chips keep the fixed Dusk safety palette.
  - Pros: owner request; safety signals never blend into the red-tinted UI; no sensor permission; predictable.
  - Cons: the time window needs a platform schedule (presentation only, not safety logic); a third scheme to test.
- **Option B — Automatic by ambient light sensor.**
  - Pros: no setup.
  - Cons: sensor noise in a dark room flips the scheme; not on every device or browser; more testing. Owner: backlog `IDEA` (Q3).
- **Option C — no night mode; Dusk only.**
  - Pros: least work.
  - Cons: the owner asked for it; Dusk text is brighter than needed at 3 AM.

Recommendation: A. **Decided: A, Automatic = time window only (owner, 2026-11-14).**

The web "Night screen" (a black cover that keeps the page awake) is a different job and is renamed **Black screen** so the two names do not compete (frames 37, 39).

### 6. Alert screen template and banner priority

**Template** (frames 08, 12, 13, 25, 26, 31): flat status strip (hidden from accessibility), caps label saying what the phone does ("Your phone is vibrating", "Loud alarm sounding", "Alarm paused"), headline, counter with its label below (spoken in words), one sentence with the next stage and its clock time, decorative progress segments with words ("Phone vibrating now"), the cause card (cause line, step 1 visible, "Try now", "More steps" folded), a quiet "Stop monitoring" text button at the end of the content, and one filled pinned action ("I'm checking" for connection stages, "Stop sound" / "Listen" for noise). The body scrolls; the action stays pinned at 200 % text. Fixed dark palettes per kind: noise wine (`#250A10`, slab `#7A1E30`), no connection red (`#2A0709`, slab `#8C1D24`), loud alarm red with hazard band (`#3A080B`, slab `#951E27`), baby battery critical amber (`#1F1209`, slab `#7A3D12`), so red stays reserved for "you can't hear the child". Slab text ≥ 7.4:1 with a mandatory 2 px light border.

**Banner priority** (frame 48), one global order: security warning › microphone silent › readiness (worst item) › baby battery low or unplugged › baby device may ring (silence status) › weak connection › Pause noise alerts › Vibrate only. Baby battery critical (< 5 %) is a full-screen alert, not a banner. At most two banners show; the rest fold into one "+N more" row (plain 48 dp text link). When the Vibrate-only banner is folded, the alert chip returns to its labelled form, so the "no sound" indicator stays visible (`parent-alerts` "Alert style"). Browser banners (sound gate, keep this page open, back from the background) rank below readiness. Two states from other active changes are placed here too: the talk-back noise pause (`add-talk-back` "Noise pause is bounded and shown") is the talk panel's status line, not a banner; the other parent's status (`multi-parent-pairings` "Other parent status") is a banner below weak connection once that change is built.

- **Option A — one global order with a limit of two** (recommended): predictable, the most dangerous state is always visible, the screen never fills with banners.
- **Option B — newest first:** easy, but a fresh "Vibrate only" could hide "microphone silent".
- **Option C — show all:** nothing hidden, but at three or more banners the monitor is a wall of warnings and the dock leaves the thumb zone.

Recommendation: A. **Decided: A (owner, 2026-11-14).**

### 7. Listen as a tap toggle

- **Option A — tap toggle** (frames 03, 04): tap starts, the whole Listen bar fills and reads "Listening · tap to stop" with a stop square; tap stops. The 60 min limit, "unavailable while not connected" and the baby's touch-wake indicator stay.
  - Pros: one motion at 3 AM, works with one hand, tremor and switch access; state readable from across the room; the forgotten-microphone risk is already bounded by the 60 min limit.
  - Cons: an accidental tap starts listening (harmless: audio only flows baby → parent, the baby shows it on touch-wake).
- **Option B — hold, slide up to lock** (today).
  - Pros: no accidental start.
  - Cons: hard at night and for older users (round 1: parent at 3 AM, grandparent, accessibility all flagged it).
- **Option C — hold to listen only.** Cons: the parent cannot put the phone down while listening.

Recommendation: A. **Decided: A.** Talk stays hold-to-talk (`add-talk-back`, a sound in the baby room needs the hold). The mockup also shows an accessibility action "Talk for up to 30 s" (frames 32, 37); it is close to the "Tap to talk" option the owner did not choose on 2026-11-11, so this change does not specify it (open question in §15).

### 8. Renames and copy rules

- "Discreet" → **"Vibrate only"**: says what happens. Chip "Alert: Sound" / "Alert: Vibrate only", banner "Vibrate only" with "Turn sound on". A one-line reminder on Home when starting monitoring with Vibrate only (owner Q4); no next-morning reset (backlog).
- "Snooze" → **"Pause noise alerts"** (10 or 30 min) with a pause icon and an **8 s Undo** snackbar: "Snooze" read as "stop everything" (round 1). The core input keeps the name `snooze`; only copy changes. Undo is offered only for a pause started while no noise event runs: in the core a pause acknowledges the running event (`link-supervision` "Noise escalation timer"), and with `multi-parent-pairings` it may reach the other parent, so Undo could not restore that event. A pause from a running alert has no Undo; ending the pause early stays possible.
- **"The child"**, never "your baby"/"your child", and a neutral person; **formal address in German**; **no name splicing**: the label pattern is "State · Name" ("Verbindung · Kinderzimmer"), never a name inside a German sentence where case endings break; **durations in words** in prose ("1 min 48 s", spoken "1 minute 48 seconds"), never `m:ss`; units with a non-breaking space; clock times as the device formats them.
- Stages named by what the phone does; no "level", "link", "peer", "L0–L3", protocol terms, IP addresses (`connection-status` "Plain copy").
- Privacy line corrected: "Sound is encrypted between your devices. No account, no cloud recording." (frame 02; the old line promised a direct path, but sound may pass a TURN relay).

Recommendation: adopt all. **Decided (owner, 2026-11-14), Q1: role names stay "Parent device" / "Baby device".**

### 9. Baby kiosk status line, shape coding and set-up confirmation

- **Always-visible status line** at `#7D7671` on black (4.7:1; the backlight keeps it dim): "Listening · Travel cot", "Parent device not responding — still trying", "Needs attention: not charging · 12 %".
- **Shape-coded marks** (frames 15, 17, 50, 51): short solid bar (44 × 6 dp, centred) = fine; no mark while waiting or within the first 20 s of a drop (level 0); dashed top edge (6 dp, 16/10 dp dashes) = still trying (level 1); 5 dp frame with a 4 s slow pulse (static with reduced motion) = no connection (level ≥ 2); bar plus a separate 10 dp square = needs attention (battery or charger). Distinguishable at arm's length without hue.
- **Luminance cap:** at minimum brightness no mark emits more than `#5A1414` at normal brightness.
- **Set-up confirmation** (frame 52): for 60 s after Start and on every touch-wake, at wake brightness (about 10 %): "Connected to Anna's phone · Listening" (the parent connection name; "Connected to the parent device" without a name). The dim countdown is not a live region.
- **During a talk** only the talk indicator shows (frame 16); status line and mark are hidden (`add-talk-back`).
- Never sound, vibration or haptics (unchanged).

Options considered: hue-only edge (today; fails colour-vision deficiency and dark-adapted eyes, round 1 CRITICAL from the grandparent and traveller reviews) and a brighter status panel (wakes the child). Recommendation: shapes plus words. **Decided.**

### 10. Tokens and typography

- **Schemes:** Dusk (default; background `#141218`, primary `#C9BCEB`), Day (white cards with a 1 px `#E0D8DF` border on `#FAF7F4`, scrim `rgba(31,27,35,.32)`), Ember (§5). Full values in the mockup's token panel (`mockup/gen_css.py`).
- **Fixed safety roles** outside the theme: info blue, warn orange, alert red, caution yellow, ok green (a dot only when calm) and the alert palettes of §6. No non-safety element within ±20° of a safety hue; brand apricot only in the logo.
- **Type:** Plus Jakarta Sans with tabular numerals; sizes 12 (caps labels) / 14 (floor for any text) / 15 / 16 / 20 / 28 / 52 (counters).
- **Motif:** the horizon line (logo, hairline under the status bar and the Home header, the monitor's sound strip with the dashed line "A sound above this line sends an alert"). The strip shows the last minute of level history; the last 5 s in full colour.
- **Font delivery:** bundled in the APK (`res/font/`) and served from the web client's own origin (`apps/web/src/assets/fonts/`), never loaded from Google Fonts at runtime: the CSP allows fonts from the own origin only (`web-client` "Browser security"), and a font request to a third party would leak the user's IP address (AGENTS.md §7.1 spirit). Subset to the scripts the locales need; fall back to the system font for scripts it lacks (zh-Hans, ja, ko, hi, ar, uk Cyrillic coverage to check).
- **Licence:** Plus Jakarta Sans is under the SIL Open Font License 1.1. The OFL is a free licence that explicitly allows bundling and embedding the font with software under any licence, including AGPL-3.0-or-later, as long as the font itself stays under the OFL, is not sold by itself and its reserved font name is respected when modified. The font files keep their OFL licence; REUSE annotations name them (`LICENSES/OFL-1.1.txt`, an `[[annotations]]` entry in `REUSE.toml`), and the About screen lists it. It is not combined into the AGPL work in a way that requires relicensing, so it is compatible with the project licence (ADR-014).

### 11. Accessibility rules

- **Alert entry:** focus moves to the headline; the status strip and caps label are hidden from accessibility so nothing is said twice; focus returns to where it was on close.
- **Live regions** announce stage changes only (polite for level 0–1, assertive from level 2, stopped peer, needs user, microphone silent); timers and countdowns (alert counter, talk time, "dims in 45 s") are never in a live region and carry a word label ("1 minute 12 seconds"). Talk speaks only its 5 s warning (`add-talk-back`).
- **200 % text:** alert bodies scroll with the action pinned; the counter drops to headline size above 1.5×; the tool row wraps to two rows (alert chip on row 1, night and gear right-aligned on row 2; traversal status → alert → night → settings); below 600 dp height at ≥ 1.5× only the status bar and Listen stay pinned. Snapshots at font scale 2.0 of frames 03, 08, 12, 13, 26 are a gate item.
- **Targets** ≥ 48 dp; dock tiles ≥ 72 dp high; buttons never wrap their label.
- **Gesture alternatives:** Listen is a toggle with a state description; Talk keeps the screen reader's double-tap-and-hold (`add-talk-back` design §9; a timed-talk action is an open question, §15); the kiosk has an "Unlock" accessibility action with a confirmation; sheets have a visible Close and a dismiss action.
- **Disclosures** ("More steps") are buttons with an expanded state; focus goes to the first step when opened. The icon-only alert chip says "Alerts for sounds: Vibrate only, Change"; "+N more" says "2 more notices: …".
- **Back:** monitor → app to background, never stops monitoring; full-screen alert → nothing; sheet → closes; Settings → monitor. Web: confirm before leaving while monitoring (`web-client` "Background loss is reported").
- **Stop confirm** opened from a red screen silences and acknowledges nothing; "Keep monitoring", back and scrim return to the unchanged alert. From level 2 "Wrong connection?" opens the same confirm; only at levels 0–1 it stops with one tap (`connection-status` "Leaving from the alarm needs confirmation").
- Information is never drawn as a disabled button ("Talk again at 03:14" is an outlined status slot at full contrast).

### 12. Compose and Svelte mapping

- **Android:** one `GuardedSleepTheme` with three M3 `ColorScheme`s (Dusk, Day, Ember) built from the tokens, a `Typography` on the bundled font with `fontFeatureSettings = "tnum"`, and a separate `SafetyColors` object provided through a `CompositionLocal` that **does not change with the scheme** (Ember never touches it). Components: `StatusBar`, `AlertTemplate`, `BannerStack` (takes the ranked list and the limit), `SoundStrip`, `Dock`, `ToolRow`, `KioskMark`. Stable `testTag`s (snake_case, shared with web). The banner ranking is a pure function in `ui-contract` (presentation order, not safety logic) with JVM tests.
- **Web:** CSS custom properties per scheme on `:root[data-scheme=dusk|day|ember]` and a separate `--safety-*` set that no scheme overrides; the scheme attribute is set by an inline-free bootstrap before the first paint (CSP: no inline script, so a tiny module loaded first). Svelte components mirror the Android ones with the same test ids; the banner ranking is a TS function with Vitest, mirroring the Kotlin one (contract mirror test).
- **Layer rules:** UI renders contract models only; night-mode schedule and readiness ranking feed the State layer from Platform; the core is untouched apart from the two read-only status fields (§4).

### 13. Rollout and implementation slicing

Each slice is one PR, green on its own and self-consistent, behind no flag (alpha). Every slice ships the copy it renders in all 20 catalogues (critical keys in every locale, AGENTS.md §5.2a), so no intermediate PR drops a locale or shows a screen without copy:

- **Slice 1, Foundation:** tokens, schemes, safety colours (level 0 mapped to `SafetyColors.info` already here, so yellow disappears), font, `ui-appearance` basics.
- **Slice 2, Status and alerts:** core status fields, status bar on every parent screen, level-only mapping with blue/orange words, alert template, connection alert screens with troubleshooter, acknowledged screen, restored card until OK, the stop confirmation and "Wrong connection?" rule (so the template's Stop slot never exists without its confirm), announcements.
- **Slice 3, Monitor:** sound strip, dock with Listen toggle, tool row, banner stack and order, readiness on the monitor, Pause with Undo, Vibrate-only renames, noise and battery alerts on the template.
- **Slice 4, Settings and Home restyle within the built flow:** Settings split, read-only connections, Open at start page (built behaviour), More sheet, back behaviour, Vibrate-only line; the built role screen and "Switch mode" stay, restyled.
- **Slice 4b, One Home with both roles:** only after task 0.4 (the `alternate-roles-and-apk-size` and `parent-pairing-entry` requirements are archived and reworded); until then those binding requirements win.
- **Slice 5, Baby kiosk:** status line, marks, luminance cap, set-up confirmation, kiosk delta (rebased on `add-talk-back`).
- **Slice 6, Night mode and web specifics:** Ember, time window, Black screen, browser sound gate and banners.

Group 7 of tasks.md is a review pass (German review, unused keys), not a copy drop; baselines are re-recorded per slice in the pinned image.

## Risks / Trade-offs

- **Familiarity loss:** alpha testers learn new names (Vibrate only, Pause). Mitigation: names say what happens; Undo after pausing.
- **Translation length:** German and other long locales stress the tool row and dock; the German check frame 45 and the 200 % rules cover it; the German dock label shortens to "Pausieren" with the full text in the accessibility label.
- **Tap-to-listen accidental starts:** bounded by the 60 min limit; visible state.
- **Large diff in screenshot baselines:** re-recorded only in the pinned image, reviewed per slice.
- **Font coverage:** CJK, Devanagari and Arabic fall back to system fonts; tabular numerals then depend on the system font.
